# Build Interaction

## Overview
Unlike the `set` and `part` interactions, the `build` interaction is not triggered by the ambient assistant. It is scoped to a thread opened by [`/build`](../commands/build.md), and inside that thread the bot reads **every** message and decides for itself whether it was meant as a building instruction.

That makes its silence policy the most important thing about it. A build thread is a normal conversation as well as a workspace, so the bot must ignore the conversation completely and act only on the grammar it recognises.

## Trigger
- The session is created by the `/build` slash command, which opens a public thread and records a row in `build_sessions` keyed by the thread's channel id.
- Afterwards there is **no** trigger word, prefix or mention: every message in the thread is parsed.
- Render messages carry four buttons, whose `custom_id`s each end in the 12-character session id: `build_export:<id>`, `build_draw:<id>`, `build_undo:<id>` and `build_finish:<id>`.
- The **starter message posted inside the thread** carries that same row, so `[Draw…]` exists before the first render. Nothing about the handlers changes: they are keyed by session id and each already answers sensibly against an empty model (nothing to undo, nothing to export, an empty drawing form).
- When a part cannot be resolved, a `build_part_pick:<id>` select menu is posted, reusing the `/part` search results. It carries the session id the same way the buttons do, so the router can find the session and the handler can check the choice still belongs to it.

## Features

- **Silence Policy**: A message is only a command when its first word is a verb the language knows, or a question word. Everything else returns `Ignored` before the parser is even entered, producing no reply, no reaction and no render. A sentence that opens with a known verb but fails to parse *is* reported, with the word it stopped on. A sentence that got in only on a question word does **not**: "what do you think?" is shaped exactly like "what changed?", so an unrecognised question, or one naming something nobody has built, falls back to silence. That asymmetry is deliberate — a verb means the builder meant something, a question word does not.
- **Quoted Lines Are Never Commands**: `strip_discord_noise` (`src/build/dsl/lexer.rs`) drops any line opening with Discord's block-quote markup — `> …` or `>>> …`, the latter quoting everything to the end of the message — before the parser ever sees it. Someone quoting the bot's own instructions while asking "did this work?" would otherwise have that quoted sentence re-run as a real command.
- **Fenced Drawings Are Captured First**: A drawing is an ASCII grid, and every other stage of the lexer would destroy one — `.` and newlines are both sentence terminators (so `..bb..` collapses to `bb`, losing every position), the URL pass rejoins each line on single spaces (losing the column alignment that is the whole point), and the block-quote filter drops lines beginning `>`. So `src/build/dsl/block.rs` lifts fences out of the raw message *before* `strip_discord_noise` or `split_sentences` see it, and attaches each to the sentence in front of it as `Sentence.block`. Only a run of three or more backticks opens a captured fence; one or two are still inline code and still dropped as noise. A fence never produces a sentence of its own, so sentence indices — which `pending_lookup` is recorded against — keep meaning what they did.
- **Private Drafting**: `[Draw…]` on a render opens a modal (`build_draw_modal:<draft>`); its submission previews **ephemerally** and writes nothing. Three Discord rules shape the loop and are worth stating because they are not obvious: a modal contains only text inputs — no buttons, no select menus, no autocomplete — so parts and colours can never be picked inside the form; a modal **cannot** be opened in response to a modal submit, so `[Edit]` bounces through an ephemeral button exactly as `wizard_retry_submit` does for events; and the three-second ACK means the text preview answers first and the PNG is edited in afterwards. The late render carries the `preview_seq` it was started for and drops its edit if the draft has moved on, mirroring how `RenderState.pending` supersedes a debounced render. Drafts live in `workflow_sessions`, which is **owner-scoped** — the draft belongs to a person where the model belongs to the thread — so no schema change was needed. `[Apply]` compares the session's revision with the one previewed and refuses if they differ.
- **Editing a Legend From Outside the Form**: a modal holds only text inputs, so `/build-legend` (options autocompleted from the palette and the sticky cache) and the `[Insert…]` picker edit the draft and re-post the preview instead. `[Insert…]` is **one flow in two steps**, colour then part, because `symbol = colour part` needs both — a colour alone is not a line. The chosen colour rides between steps as its numeric LDraw code in the custom id (`build_insert_part:<draft>:<code>:<page>`), so no state is held anywhere; the router splits only on the first colon and each handler parses the rest. Pages replace themselves with `UpdateMessage` rather than posting per page, and `Back`/`Next` are disabled at the ends. **This is the only paginated list in the bot** — everywhere else truncates at 25 — so `page_count`/`page_bounds` are unit-tested for coverage without gaps and for clamping a stale out-of-range page. Both routes find the draft with `db::find_latest_workflow_session`, which is owner-scoped, and `/build-legend` opens one when there is none.
- **Feedback By Reaction**: Accepted commands get ✅, comments (`Note:` / `TODO:`) get 📝, and problems get ❓ plus one short message. This keeps the thread readable when several people are building at once.
- **Collaborative State**: The session is looked up by channel, never by owner, so every member of the thread edits the same model. This is why `build_sessions` exists rather than reusing `workflow_sessions`, whose accessors are all owner-scoped. Loading the history, interpreting the message and writing it back is guarded by a per-session lock and committed in one transaction: without that, two people building in the same second both read the same cursor, both discard the redo tail from it, and the first person's brick disappears with no error anywhere.
- **Debounced Rendering**: A burst of commands coalesces into one render, so four people typing simultaneously produce one picture rather than four. Leading edge plus trailing edge: a lone command draws at once so the thread stays responsive, and anything arriving inside `render_debounce_ms` replaces the render waiting to go out. The trailing render reloads the history when it fires, so it shows everything that landed meanwhile. `plan_render` is the pure decision; `schedule_render` is the part that talks to Discord.
- **Part Disambiguation**: A part the built-in catalogue does not cover is handed to `part_interaction`, the same function behind [`/part`](part.md). Its `SearchResults` variant supplies the dropdown, and the sentence that paused is parked on `build_sessions.pending_sentence`. Choosing an option routes to `handle_part_choice`, which rebuilds a `PartRef` from the Rebrickable result and replays the parked sentence through `process_message_with_part` — the ordinary lowering path, with the chosen element answering the lookup, so modifiers and locations behave exactly as they would for a catalogue hit. Any other message that changes the model clears the parked sentence first. A sentence carrying a drawing is parked **with its fence** — `Sentence::replay_text` re-emits it canonically, and it re-lexes to the very same sentence — because `Build from top:` on its own would mean nothing. That also caps a drawing at **one** unknown legend part: the replay carries a single chosen element and hands it to whichever entry asks first, so a second would resolve the first entry again for ever. Two or more are refused up front (`GridError::ManyUnknownParts`) rather than looping.
- **Localization**: All output is localized with `rust-i18n`. The *input* grammar is deliberately not translated — it is a language, not UI text — so verbs, colours and units stay English in every locale. A Finnish keyword table can be added later without touching the parser.
- **Help Fallbacks (`Meta::Help`)**: Asking for help with an unrecognized command or topic gracefully falls back to the general help text without causing an error.

## Internal Implementation
- `src/build/dispatch.rs` — `process_message`, the pure entry point. It returns the operations to record, the replies, the reactions and the render/export/finish flags. `Outcome::is_silent()` is the empty case, and is asserted against a table of real chat lines. `Outcome::ops_start` says which revision the operations belong at — not simply the loaded cursor, because `Undo. Add a brick.` rewinds before it appends — and `Outcome::cursor` is where the session ends up. `dispatch::Builders` maps the names people type onto Discord user ids, which is what makes `Undo alice's last edit.` able to match the log at all.
- `src/build/draft.rs` — the private drafting loop's pure half: `DraftFields`, the text they `assemble` into, `split_fields` for prefilling from the current model, and `preview`. A preview is `dispatch::process_message` against `history.clone()` with `persist` skipped — one interpreter, so a preview cannot mean something different from the apply.
- `src/build/dsl/block.rs` — fence capture, and sorting a block into its legend and layers.
- `src/build/grid.rs` — gathers a drawing's cells into whole parts, greedily from the top left, and maps them into LDraw coordinates for each of the six views.
- `src/build/textview.rs` — the inverse: the model drawn back as a grid, in the syntax it is typed in. Pure, and needs neither the LDraw library nor the rasterizer, so it works in box mode too.
- `src/build/propose.rs` — where a part could plausibly go, when the builder named one without saying. Enumerates and ranks anchors; every candidate is put on the grid and settled by `legal`, so a proposal cannot be somewhere illegal. A *batch* is the unit — one brick, an arrangement of several, or a whole drawn block — which is why one engine answers the bare-part sentence, the location-less drawing and the `[Place…]` button in the drafting loop alike. The dialog itself is `session::offer_proposals`, backed by a `workflow_sessions` row; it is **public** rather than ephemeral because a chat message carries no interaction token, exactly as `offer_part_choices` is.
- `src/build/legal.rs` — what counts as a legal connection, and how to correct one that is not: the stud/plate lattice, and settling a batch onto the nearest free resting place. `dispatch` calls `legalize` between lowering and applying, and records the *corrected* operation, so the revision log is legal by construction and replay never has to re-check anything. There is no stud-and-anti-stud model to consult — legality is expressed in the same integer boxes as everything else, which is enough for System parts.
- `src/build/report.rs` — every user-facing string, in both locale files.
- `src/build/session.rs` — the Discord shell: thread creation, persistence, the render loop and the buttons. Its only decisions are about pacing and locking, both of which are separated into pure helpers (`plan_render`, `should_render_now`).
- `src/commands/build.rs` — the command declaration and the pure message builders.
- `src/db/build.rs` — session and revision storage, looked up by channel id.
- `src/main.rs` — the session lookup is hoisted **above** the `ambient_channel_ids` gate in the `message` handler. A thread has its own channel id, so it is never in that list; without the hoist every build command would be silently dropped. Returning early also keeps build traffic out of the ambient assistant's two-hour per-user cooldown.
- `src/workflows/mod.rs` — routes the three `build_*` button ids to `handle_build_button`, and `build_part_pick` to `handle_part_choice`.
